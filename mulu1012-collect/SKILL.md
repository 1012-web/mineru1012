# 从链接到上线

**输入**：一个导航站链接（图书馆电子资源列表、学科门户、数据库导航页），可能附带范围或数量要求。
**输出**：mulu.1012.wiki 上的 `sites` 题录 + 批次目录里的完整留痕。

```
采集 → 查重 → 填充 → 字段复检 → 上传
```

| 环节 | 做什么 | 产出 | 详细 |
|---|---|---|---|
| 一 采集 | 探测站点、抓取 | 各站采集 JSON + `任务说明.md` | §1 |
| 二 查重 | 汇进一张表，标批次内与站内的重复 | `批次总目.xlsx` + 查重结论 jsonl | §2 |
| 三 填充 | 在同一张表上补语义字段 | 填好的 `批次总目.xlsx` | §3 |
| 三半 复检 | 对照字段指南检查整表与源数据 | `字段复检报告.json` | §3.5 |
| 四 上传 | REST 写入 WordPress 并回填 WPID | WPID + 回读复核 | §4 |

汇总表放在查重环节，因为跨源比对必须在一张表上做；填充在同一张表上继续，不再重新组织数据。

**AI 全程执行，只在这些节点停下来等用户，其余自决：**

| 节点 | 等什么 |
|---|---|
| 探测后 | 字段多到离谱、或要为详情页多发一轮请求时，问值不值得 |
| 查重后 | 「疑似重复」和把握 < 70 的结论，用户拍板 |
| 填充前 | AI 语义判断与边界模糊项，呈现确认后才写回表 |
| 上传前 | dry-run 结果确认后才正式上传 |

## 批次目录

每次采集在 `00-采集批次/` 下建一个批次：`{序号}-{站点名}（{YYYYMMDD}）`。序号两位，取现有最大值加一，**不回收不复用**；括号用中文全角。

**站点名用资源自己的通行名**：中文资源用中文（`国家图书馆`），外文资源用原名（`crossasia`、`DBIS`），不硬译也不转拼音——判据是研究者平时怎么称呼它。

```
单站点批次                                多站点批次（一批采多个馆）
00-采集批次/NN-上海图书馆（YYYYMMDD）/      00-采集批次/NN-公立图书馆采集（YYYYMMDD）/
├── 上海图书馆（195）.json                 ├── 01-采集源数据/
├── 上海图书馆.progress.json               │   ├── 01-国家图书馆（227）.json
├── 02-查重/                              │   └── 02-上海图书馆（195）.json
├── 批次总目.xlsx                          ├── 02-查重/
└── 任务说明.md                            ├── 批次总目.xlsx
                                          └── 任务说明.md
```

- 采集 JSON 文件名标注**采集总数**；多站点批次内各站序号独立从 01 起
- `任务说明.md` 必有：批次概述 + 各站探测结果（见 1.1）
- `02-查重/` 存查重结论 jsonl（见 2.4）
- 采集脚本只在逐页采集这类复杂逻辑时保留副本；一次拿全的 API 靠 `任务说明.md` 里的记录即可复现

# §1 环节一 · 采集

## 1.1 探测

开采前必须回答两件事，结果写进 `任务说明.md`。

**站点结构**——抓列表页首页看三样：

- **有没有 CSV/API 导出**：有就直接用，别爬 HTML
- **有没有详情页**（`href` 含 resource/detail/database + 数字）：有则列表页先拿 URL 清单、再逐条抓详情，多一轮请求
- **有没有 JS 数据调用**（`onclick="openRes(...)"` 之类）：入口 URL、资源 ID、授权角色常常**只存在于 JS 函数参数里**，光看渲染文本会漏掉一半字段

**字段上限**——取一条记录的 HTML 块，枚举所有可提取的信息点：文本节点、属性（`title`/`alt`/`href`/`src`/`data-*`）、JS 函数调用的参数。各站差距极大（详情页站可达 26 个字段，列表页站可能只有 10 个），先知道天花板才能判断要不要为详情页多花一轮请求。

`任务说明.md` 必答：站点结构（上面三问）、列表页 URL、字段上限与可采字段清单、分页机制、总记录数、反爬（限流/验证码/间歇 5xx）、SSL（是否只能走 HTTP）。**不凭记忆判断字段是否存在，必须实抓样本验证。**

完整探测步骤与检查清单见 [`site-probing.md`](references/site-probing.md)。

## 1.2 采什么

**默认全采**——探测到的信息点一律采下来。采集成本几乎全在请求上，多存字段不额外花钱；漏采的字段日后想补就得重跑整站。

只有两种情况先问用户：字段多到离谱（几十个且大半是站点内部的排序号、图标尺寸），或某字段要额外一轮请求才能拿到。

## 1.3 怎么采

| 要素 | 取值 |
|---|---|
| 输出 | **JSON**——后续环节的脚本只吃 JSON |
| 并发 | **1**（顺序请求）。图书馆门户普遍扛不住并发；实测确认不限流的大站才试着上调，出现 5xx 立刻降回 |
| 断点续传 | 每页落盘（`*.progress.json`），可重跑；一次拿全的 API 除外 |
| 错误处理 | 3 次重试 + 2s/4s/6s 递增退避 |
| 技术栈 | PowerShell 自带的网络请求命令 `Invoke-WebRequest` + 正则提取，不装第三方解析库 |

**先采 5 条验证字段提取正确，再全量。** 脚本框架与适配新站点的要点见 [`scraper-template.md`](references/scraper-template.md)；一个完整实例（JS 参数提取、502 重试、sso 代理坑）见 [`图书馆列表站-实例（国家图书馆）.md`](<references/图书馆列表站-实例（国家图书馆）.md>)。

## 1.4 产出契约

**采集忠实于源站原貌，不强加统一字段结构。** 源站字段叫什么、嵌在第几层，就照原样存——原始字段本身是证据。不同站点的字段结构各不相同是正常的，环节二用每站一个 `--field-map` 消化；字段映射是那时候的事，不是采集的事。

采集阶段唯一的约束：

- 产物落在批次目录里，不散在项目根目录
- 文件名标注采集总数
- 找不到证据的字段留空，不写 `待确认` / `未知` / `N/A`

# §2 环节二 · 查重

```
各站采集 JSON → 汇总进模板(2.2) → 批次总目.xlsx → 跨源查重(2.3) → 入库查重(2.4)
```

**不做站内自查重**——采集层删行不可逆，而「四部丛刊」与「四部丛刊增补版」这类看着重复的往往该独立收录。同源条目的合并留到跨源与上传阶段，那两处是合并不删行。采集 JSON 直接进汇总。

## 2.1 两种查重，口径相反

| | 跨源查重 | 入库查重 |
|---|---|---|
| 问什么 | 批次里几个馆共有同一个库吗 | 站上是不是已经收过 |
| 比对对象 | 批次总目全表 | `总目-与站点同步.xlsx` |
| 口径 | **不删**，只标记 | 保守：宁可重复审，不轻易判重 |

跨源重复是有价值的事实——「国图和上图都买了 CNKI」决定「有授权的图书馆」怎么填，删掉就丢了。

## 2.2 汇总进批次总目

把各站采集记录填进 `批次总目模板.xlsx`（仓库根目录）的「条目表」，每条资源一行，全批次共用一份。模板 7 个 Sheet：说明、条目表（47 列）、别名明细、机构授权明细、协作者导语、获奖明细、词表速查。

**这一步只填结构性字段，语义判断留给环节三。** 脚本不认死字段名，靠每站一个 `--field-map`（该站字段叫什么、记录数组在哪、访问方式怎么判、备注收哪些原始标签），样例见 [`映射-国家图书馆.json`](references/映射-国家图书馆.json)，完整结构说明在脚本头部。

```bash
# 第一个站
python scripts/build_batch_mulu.py \
  --json "00-采集批次/NN-.../01-采集源数据/01-国家图书馆（227）.json" \
  --out "00-采集批次/NN-.../批次总目.xlsx" \
  --field-map "<该站映射.json>" \
  --batch-name "<批次目录名>" --source-name "国家图书馆" \
  --source-url "<该站电子资源导航页>" --check-date YYYY-MM-DD \
  --id-prefix NLC --sso-host sso1.nlc.cn --expect 227

# 第二个站起：必须加 --append，否则会清空前面所有站的行
python scripts/build_batch_mulu.py ... --id-prefix SHL --append
```

`--expect N` 与实际条数对不上就报错退出，防止拿错文件（文件名标数与内容不符时当场拦住）。

### 结构性字段的取值

| 列 | 取值 |
|---|---|
| 简体中文名 | **一律写简体中文名**。优先采用来源中已有的简体中文题名；只有外文、繁体、日文、韩文或转写名时，根据原名、替代题名和简介译写为简体中文。原名仍进入「别名明细」，AI 评语记录译写依据与置信度 |
| 机构内名称 | 该馆页面采用的名称字段；它是（库×馆）关系属性，不并入简体中文名或别名 |
| 入口页url | 主入口地址。**代理跳转（sso、EZproxy、登录跳转）不收录**，改用直连地址并在 AI 评语注明 |
| 访问方式 | 仅局域网→`仅馆内访问`；互联网→`可馆外访问`；并存则并选；机构订购的再并选 `需授权＞机构订购` |
| 该馆访问方式 | `可馆外` / `仅馆内` / `未说明`。判不出就填 `未说明` 并进评语，不猜 |
| 简介 | 该站描述为符合指南的简体中文时写入；外文或繁体描述只保留在原始采集文件，主列留空并进 AI 评语，待人工编写 |
| 官网介绍 / 官网介绍出处url | **留空**（见下方说明） |
| 载体 | `网页` |
| 采集批次 / 来源名称 / 来源URL | 批次名 / 站名 / 导航页 URL |
| 复核状态 | `待复核` |
| 条目ID | `{站点缩写}-{三位序号}`，如 `NLC-001` |
| 授权机构（本批次） | 本批次的馆名，整列相同 |
| 授权页url | 该馆**电子资源导航页**，不是单库详情页。**红线：不存代理地址** |
| 授权范围 | 该馆只买了本库一部分时填，买全库留空。见下方「部分采购怎么记」 |
| 核验日期 | 采集日期 `YYYY-MM-DD` |
| 备注（末列） | 源站**原始标签**，原样留存不翻译不归并，格式 `来源名｜分类法名：值`。这是日后映射主分类的证据 |

**无对应列的源站字段**（资源 ID、授权角色、缩略图、源站分类…）全部进备注列原始标签，不硬塞进主表其他列。

### 题名与别名硬约束

- `简体中文名` 一律写简体中文：优先顺序为来源中的简体中文题名 → 已有中文译名／别名 → 繁体转简体 → 根据原名、英文替代名和简介进行 AI 译写。
- 源站主标题不是简体中文时，原样写入「别名明细」的 `原名` 行；源站替代题名按映射归为 `译名` / `文字变体` / `缩写/代号` / `其他`。
- AI 新译名可以写入主列，但不得伪装成来源事实：AI 评语写明「根据哪些原名／别名译写」，原名必须可追溯；译写置信度低于 70 时列入人工确认项。
- 只有现有信息不足以形成可辨识译名时才留空，并在 AI 评语写「题名证据不足，待人工命名」；不能把外文原名直接顶替进主列。
- 别名类型和语言都属判断字段：字段映射能证明时填写；证明不了就填 `其他` 或留空，不靠字符外观猜语言。
- 每个被改写、翻译或移出主列的源站题名都必须仍可在「别名明细」或原始采集文件中追溯。

> **部分采购怎么记**：馆方清单里常出现「XX数据库（少儿版）」「XX第1-4期」「仅管理学期刊库」这类，说明该馆只买了一部分。按**这部分能不能被单独采购**划线：
> - **能单独采购且有独立入口的子库** → 另建条目 ＋ 填「母库」，授权挂在子库条目上（万方学位论文库 vs 期刊库、EBSCO 的 ASU vs BSU、Emerald 各产品）
> - **期次、版本这类拆不成子库的** → 合并成一条，把版本写进机构授权明细的「授权范围」（第1-4期、初集、党建版、教育版）
>
> 「授权范围」只写**买了什么**。`移动端` 是访问端不是范围；`仅限馆内访问`／`需IP登录` 是访问条件（归访问方式）；`包库`／`本地镜像` 是部署方式（归备注）——三类都不进这一列。

> **导航页抓来的简体中文介绍进「简介」，不进「官网介绍」**：外文或繁体描述保留在原始采集文件，不能直接占用要求简体中文的「简介」。导航页文字是第三方压缩改写过的；「官网介绍」按定义只收资源自身官网的完整连续原文。混填的话，站上展示的「官网介绍」名不副实，日后想补真原文也分不清哪些被加工过。官网原文的抓取属编目阶段。

## 2.3 跨源查重

表建好后在全表找几个馆共有的库（CNKI、万方、超星这类商业库必然多馆重复）。**只标记不删行**：在备注或单独一列记重复组，上传时合并为一条 `sites`、把各馆汇进「机构授权明细」。

## 2.4 入库查重（对站点总目）

三层漏斗——脚本负责排序和给候选，AI 负责判断，用户负责拍板：

```
脚本粗筛（scripts/site_dedup.py）—— 给档位和候选，不是结论
  已存在  URL 规范化后相同 / 名称·别名规范化后相同
  疑似    名称包含、相似度 ≥75%、或入口同域名
  未匹配  三条都对不上
      ↓
AI 复核 —— 全部条目都要过，一档都不能跳
      ↓
用户拍板 —— 只看「疑似重复」与把握 < 70 的
```

**三档都要 AI 复核，没有免检档**——实测（227 条对总目 2242 条）：「未匹配」档 18.7% 是漏判，「已存在」档 4.3% 是误判。脚本档位只用来排序和提供候选。

AI 复核判据：

- 结论五类：已存在 / 疑似重复 / 母库已存在子库未单列 / 未收录 / 证据不足
- 只有**同 URL** 或**名称＋内容范围高度一致**才判已存在；同 URL 也要核名称——平台级域名会撞车（Wiley、ProQuest、NewsBank、CNKI 各子库共用域名）
- 同机构、同平台、同域名**不能单独**判重复；英文通用词重合不算证据
- 有独立名称、独立入口、独立检索价值的子库，母库已存在也不排除
- 复核「未匹配」档时**别只看脚本给的候选**——那正是脚本没找到的地方。重点想四类字面比对必漏的：英文原名↔中文站内名、缩写↔全称、带厂商前缀↔不带（`爱如生·`/`GALE·`/`AMD·`/`文献总库·`）、同产品不同版本或年代段
- 把握写 0–100 整数；低于 70 的必须让用户看
- **归一化分两档，别混用**：温和档（去标点大小写）可以下结论；宽口径档（剥厂商前缀/括注/通用后缀）只配产候选——它会把 `畅想之星全民阅读库` 和 `超星全民阅读库` 撞成同一个键。详见 [`名称匹配与语义判定.md`](references/名称匹配与语义判定.md)
- **判定指向的 WPID 必须出现在 hits 里**，否则表上「无候选却判了已存在」，人没法复核
- **证据后补的，要重跑一轮**：简介/主办方补齐后，对未收录/证据不足/疑似重复三类重判（跳过 `by=user`）

### 结论的存放与人工确认

| | 位置 | 角色 |
|---|---|---|
| 真源 | `02-查重/查重结论-{站名}.jsonl` | 一行一条，可 diff、可跨批次拼接 |
| 确认口 | `批次总目.xlsx` 的「站内查重」sheet | 渲染产物 + 用户填改判的地方 |

jsonl 每行含：`id / source / name / entry / brief / tier / hits / verdict / wpid / confidence / reason / by / at / note`。`tier` 是脚本档位，`verdict` 是最终结论，分开存才能事后评估脚本准确率。**`by` 决定覆盖优先级：`user` > `ai` > `script`**——用户的判断谁都不许覆盖。

```bash
# 粗筛 + 刷新确认表（跑一次 = 回收人工列 → 更新结论 → 重渲染，重复跑安全）
python scripts/site_dedup.py \
  --json "<该站采集 JSON>" --field-map "<该站映射.json>" --source-name "<站名>" \
  --dedup-dir "00-采集批次/NN-.../02-查重" --xlsx "00-采集批次/NN-.../批次总目.xlsx"

# AI 审完 jsonl 后只刷新表格：省掉 --json/--field-map/--source-name
```

「站内查重」sheet：判重靠**名字＋主办者＋链接**，两边这三样都在同一行；名称两列加粗放大；「采集简介」默认隐藏；疑似档排最前；把握 < 70 标红。用户只填最后三列（人工判定 / 人工WPID / 人工备注），**留空＝同意 AI**；填完重跑命令即回收。改完关掉 Excel 再跑——文件锁着写不进去。

脚本会自动对线上做快照时效检查（线上条数比上次基线多就提醒重新导出同步文件；离线静默跳过，`--no-freshness-check` 可关）。

### 结论怎么用（都不删行）

- **已存在** → 上传时不新建；该馆授权汇进已有 WPID 的「机构授权明细」
- **未收录** → 走正常上传

「未匹配」是脚本档位，「未收录」是三层走完的结论，报告里不得混用。比对基准是本地同步文件——隔了几天或其他批次刚上传过，先重新导出 `总目-与站点同步.xlsx` 再跑。

# §3 环节三 · 填充

环节二结束时表已存在、结构性字段已填好。本环节在**同一张表**上补语义字段。

**两条铁律**（吃过亏，见 [`名称匹配与语义判定.md`](references/名称匹配与语义判定.md) §四）：

1. **先补证据，再判语义**。简介、主办方、入口 url 这些证据如果是后补的，补齐之前跑出来的判定全部作废——「自建/特色库？」用规则在简介补齐前跑，43% 判成存疑且有系统性误判。
2. **判定归 AI 逐条做，脚本只产候选**。规则用的永远是「跑的那一刻手上有的证据」，证据一变就过期；语义判断本来就要读懂内容。脚本负责归一化、产候选、渲染清单、写回表。

## 3.1 字段规则的真源在代码仓

**本 skill 不复述字段规则，只引用**——压缩必然失真（失真的规则会静默写错数据），复制会造出第二真源（字段改造期间静默分叉）。题录库与代码仓同在 `D:\projects\` 下，直接读绝对路径：

| 文档 | 回答什么 | 路径 |
|---|---|---|
| **字段填写指南.md** | 字段怎么填：受控词表、网址类型判别决策树、访问方式并选规则、AI 填写约定 | `D:\projects\mulu1012\00-开发文档\字段填写指南.md` |
| **sites字段一览.md** | 字段模型：有哪些字段、存在哪层、实际键名、分区 | `D:\projects\mulu1012\00-开发文档\sites字段一览.md` |
| 词项树快照.md | 词表实况：当前有哪些词、各挂多少条 | `D:\projects\mulu1012\00-开发文档\词项树快照.md` |

判字段取值前**先读对应小节**，不凭印象填。本 skill 当前对齐：`字段填写指南.md`＝2026-08-02（B1–B5 改造版）、`sites字段一览.md`＝2026-08-01 盘点；文档日期更新就以文档为准，并回来更新这一行。

## 3.2 本环节 AI 判断的字段

取值规则去 3.1 的文档查；这里只列职责范围与本场景特有的判据：

- **主办方**：按入口 URL 域名、名称括注、描述判断。词表已有词优先复用；能确定但词表没有的**新建全称**（不用简称）；信息不足留空并进评语。
- **网址类型**：按 `字段填写指南.md` §三的决策树**逐条走**（依次问、命中即停），不按资源类型套例子。
- **网站语言 / 国家地区**：外文库→对应语言与国家；中文库→`简体中文` / `中国`。
- **自建/特色库？**（是/否/存疑）：是＝该馆自建的特色库、数字特藏（主办方通常就是这个馆）；否＝商业外购产品。**看主办方与介绍文字，不看挂在馆网页哪个栏目**。拿不准填 `存疑`。
- **史学数据库？**（是/否/存疑）：是＝内容主体是史料、史学文献或史学研究工具，或跨学科但对史学研究有实际用途（报刊全文库、地方志库、综合学术平台）；否＝纯法律/医学/理工/当代统计/大众阅读。拿不准填 `存疑`，不猜。

> 后两条是本 skill 特有的（只服务「按馆采集」场景），所以写在这里而非引用。

## 3.3 判断结果写回表

判断结果写成判断 JSON（键＝该站记录 id，样例见 [`实例-国家图书馆判断.json`](references/实例-国家图书馆判断.json)），然后**带 `--judgments` 重跑 2.2 的命令**——源数据没变，重跑幂等，表里多出语义列。

**不要在 xlsx 里手工改数据**——重跑会整表覆盖。要改就改源 JSON、`--field-map` 或判断 JSON 后重跑（「站内查重」sheet 的人工三列除外，那里有回收机制）。

**AI 判断与边界模糊项必须先呈现用户确认再写回。** 字段对不上、词表没有合适词、主办方无法确定 → 问用户；未确认前不猜。AI 评语记录：存疑字段、缺依据项、代理链接未收录说明。

## 3.4 编目字段（本环节留空）

主分类、特色史料、研究主题、专门史、时期、国别/区域史、材料类型、材料语言、收录年限、正式介绍、**官网介绍**、母库、系列、基金项目、上线时间、评级、作者/编纂者——本环节留空，编目阶段再填。

留空是**分工**不是规则缺失：这些字段的取值规则同样在 `字段填写指南.md` §一，但判它们要读资源本体（官网原文、收录范围、材料形态），采集拿到的证据不够。编目时按指南填；层级分类法必须写满祖先链，见 [`编目-分类法层级规则.md`](references/编目-分类法层级规则.md)。

（「简介」不在此列——环节二已从源站描述填好。）

## 3.5 字段复检门

填充完成后、上传前必须独立跑一轮字段复检。生成规则负责尽量不写错，复检负责发现跨字段冲突和遗漏；两者不能互相替代。

```bash
python scripts/validate_batch_mulu.py \
  --xlsx "00-采集批次/NN-.../批次总目.xlsx" \
  --source-json "<该站采集 JSON>" \
  --report "00-采集批次/NN-.../字段复检报告.json"
```

复检至少检查：47 列表头与行数、条目 ID 唯一、简体中文名不被外文/繁体题名占用、无简体中文名时原名已进入别名、必填字段、受控词表、代理/登录 URL、AI 评分与评语、明细表外键、源记录总数与总目行数一致。

**报告 `status=fail` 时不得进入上传。** 主列空值算未完成项，应先根据原名、别名和简介补做 AI 译写；低置信译名交人工确认后重跑复检。不能为了让报告通过而把外文原名塞回主列。

# §4 环节四 · 上传

**通道：`mulu1012-suite` 的 catalog-import REST——`POST /mulu1012/v1/catalog-import/preflight` 验证（即 dry-run），用户确认后 `/apply` 写入。** 不用 `mulu-database-importer` 的 ability，也不用 `mulu_taxonomy_terms` 参数（都仍在线但已弃用）。机制与检查清单见 [`wordpress-json-upload.md`](references/wordpress-json-upload.md)。

要点：

- 入参契约与受控清单看代码仓 `00-开发文档/插件说明（plugins）/sites题录批量导入（catalog-import）.md`；**字段键名与存放层逐字段对照 `sites字段一览.md` §二，不凭记忆拼 JSON**
- **先小批 preflight，逐条核对回执**（尤其 `created_terms`——不该新建的词出现就停）；suite 本地代码的白名单与线上有出入，以线上与回执为准
- 层级分类法写满祖先链、拆成多条路径；词名与站上完全一致
- 入库查重结论分流：**已存在不新建**，该馆授权汇进已有 WPID；只有「未收录」才新建条目
- **WPID 只能来自线上响应或 REST 回读**，绝不凭记忆填；回填后再回读复核一次
- 密钥文件 `C:\Users\yan\.codex-secrets\mulu1012-wordpress.json` 只读取，内容绝不进代码、报告、对话
- 不直接写 WordPress MySQL

## 硬规则

**通用**
- 文档正文一律中文；文件名与文件夹名用资源自己的通行名（中文资源用中文，外文资源用原名）。
- 找不到证据的字段留空，不写 `待确认` / `未知` / `N/A`。
- 不在脚本、输出、报告、对话中写入密钥、账号密码。

**采集**
- 采集结果落在批次目录，每批必有含探测结果的 `任务说明.md`。
- 先实抓样本探明结构与字段上限，再开采；先采 5 条验证提取，再全量。
- 默认全采探测到的字段；只在字段多到离谱或需额外请求时问用户。
- 逐页采集必须支持断点续传。

**查重**
- 不做站内自查重，采集 JSON 直接进汇总；合并留到跨源与上传阶段。
- 多站点批次第二个站起必须 `--append`，否则清空前面所有站的行。
- 入库查重三档全部 AI 复核；「未匹配」是脚本档位，「未收录」是最终结论，不得混用。
- 跨源重复与入库重复只标记不删行。
- 入口页url 与授权页url 不收录 sso / EZproxy / 登录跳转地址。
- 不在 xlsx 手工改数据（「站内查重」人工三列除外）；改源文件后重跑。

**填充**
- 字段取值先读代码仓两份文档，不凭 skill 或记忆。
- 简体中文名只收简体中文题名；其他题名进别名明细，源站原名必须可追溯。
- 先补证据再判语义字段；证据后补的要重跑受影响的判定。
- 语义字段的判定 AI 逐条做，脚本只产候选，判定落成可 diff 的 JSON。
- AI 判断与边界模糊项先经用户确认再写回。
- 层级分类法写满祖先链；当心词树里的同名孤儿词。
- 封闭词表约束的是填写方，不是禁止扩充——扩词由维护者在后台做，之后重跑词项树快照。
- 用户开始人工审查后，只能原地改表，不得从模板重建工作簿。
- 上传前必须生成 `字段复检报告.json`；报告失败不得上传。

**上传**
- 只走 suite 的 `preflight` → `apply`；先小批试跑并核对回执，用户确认后才 apply。
- 已存在条目不新建，汇授权进已有 WPID。
- WPID 只来自线上响应或回读。
- 不直接写 WordPress MySQL。
